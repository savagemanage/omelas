# GitHub Pages deployment for the Omelasian Bible via MkDocs Material (v1)

Configures the repo to publish all nine books (54 chapters) as a static site on GitHub Pages without touching any prose. The approach builds the existing Markdown with MkDocs 1.6 + Material, deploying through a GitHub Actions workflow on every push to `main`. Because MkDocs 1.6 forbids `docs_dir` at the repo root, a small Python script materializes a `docs/` directory of symlinks (`index.md` -> `docs_home.md`, `books` -> `books`) so the original files stay byte-identical on disk. A Korean landing page lists every book, and `mkdocs.yml` carries a full hand-written nav covering all 54 chapters plus 9 book indexes.

Watch for: the `exclude_docs` block in `mkdocs.yml` is dead config given the symlink tree (confirmed); `canon/` prose is not published anywhere (confirmed, likely intentional); DEPLOY.md's closing note claims the workflow ships via PR while it was committed straight to `main` (confirmed, doc-vs-reality mismatch); the hand-maintained nav duplicates the on-disk chapter structure and will silently drift if chapters are added (likely).

**Verdict**: APPROVED

## High-level view

The site is browsable end to end. A fresh `build_docs_tree.py` + `mkdocs build --strict` produces 63 rendered pages (54 chapters + 9 book indexes), `site/index.html` carries `<html lang="ko">` and the correct canonical `https://savagemanage.github.io/omelas/`, the home page links to all nine book indexes, and book-index links resolve to working directory-style chapter URLs. The strict build exits 0 with only a cosmetic Material-team warning about a future MkDocs 2.0.

The docs-tree strategy is the load-bearing design choice. Rather than move or copy prose, the script builds a `docs/` directory containing two relative symlinks, keeping every book and chapter file untouched (confirmed by an empty `git diff` on `books/`, `canon/`, and the English originals) and staying safe to re-run since `docs/` is rebuilt each time. The cost is a build that only works after the script runs, which the workflow and DEPLOY.md both account for.

The deploy workflow is correct and complete: `contents: read` / `pages: write` / `id-token: write` permissions, the required `build_docs_tree.py` step before `mkdocs build --strict`, current action versions (`configure-pages@v5`, `upload-pages-artifact@v3`, `deploy-pages@v4`), and a split build/deploy job using the `github-pages` environment. It needs the one-time "Source: GitHub Actions" setting, which DEPLOY.md documents.

The known gaps are maintainability rather than correctness. The nav in `mkdocs.yml` restates the entire on-disk chapter layout by hand, so new chapters won't appear unless the nav is edited too. The `exclude_docs` block references paths that never enter the symlink tree. And `canon/` is excluded from the site entirely, which is consistent with "all books" but means that supporting material is invisible.

<summary>Details</summary>

### Symlink docs-tree to preserve prose byte-for-byte

MkDocs 1.6 rejects a `docs_dir` at the repo root and rejects a `site_dir` nested inside `docs_dir`, yet the requirement is to publish files that live at the root (`books/`) without editing them. `build_docs_tree.py` resolves this by creating `docs/` and populating it with two relative symlinks:

```
docs/
  index.md  -> ../docs_home.md
  books     -> ../books
```

Relative targets (`os.path.relpath`) keep the tree valid regardless of where the repo is checked out. Because symlinks are new inodes, no prose is copied or rewritten; the empty `git diff` on `books/`, `canon/`, `README.md`, `ideation.md`, and `page-1.md` confirms the originals are untouched. The script rebuilds `docs/` from scratch on each run, so repeated local and CI runs are idempotent.

One robustness caveat: symlink-based trees depend on the runtime supporting symlinks — fine on the `ubuntu-latest` runner and on local Unix dev, but a Windows checkout without developer mode would break with a confusing local failure. `possible` — not exercised in this repo's CI, would only surface for a Windows contributor.

### End-to-end browsability of all nine books

A from-scratch build produces 63 `index.html` pages under `site/books/` — 54 chapters plus 9 book indexes — matching the 54 chapter files and 9 `00-index.md` files on disk. Book-index pages link to their chapters with plain relative names (`](chapter-01.md)`), which MkDocs rewrites under `use_directory_urls: true` to working `books/01-revelation/chapter-01/` URLs. No book index or chapter links out to `canon/` or parent directories, so there are no dangling cross-references that `--strict` would reject. `confirmed`.

### Version pins guard against MkDocs 2.0

`requirements.txt` pins `mkdocs>=1.6,<2` and `mkdocs-material>=9.5,<10`; the installed resolution here was mkdocs 1.6.1 and mkdocs-material 9.7.7. The upper bounds guard against the MkDocs 2.0 / Material rewrite the build warning references, so an unattended CI run won't silently pull an incompatible major. `confirmed`.

### Maintainability gaps

The `exclude_docs` block lists `.agents/`, `.git/`, and `site/`, but the symlink tree only ever exposes `index.md` and `books/`, so those exclusions match nothing — dead config that implies the build scans the repo root when it does not. Separately, the entire navigation is written out by hand in `mkdocs.yml`, one entry per chapter with its Korean title. This gives full control over ordering and titles, but it duplicates the on-disk structure: a new chapter file won't surface unless the nav is edited, and under `--strict` an un-navigated page can fail the build outright. If the chapter set is essentially frozen this is a non-issue; if chapters will keep being added, a generation step (or an auto-nav plugin) would remove the drift risk. `confirmed`.

`canon/` holds Korean prose (`story-bible-ko.md`, `ideation-ko.md`, `page-1-ko.md`, `README-ko.md`) that appears in neither the nav nor the docs tree, so it is not published. The requirement was "all books," and canon is supporting material rather than a book, so this scoping is defensible — but worth an explicit confirmation since the material is otherwise invisible on the site. `confirmed` that it's excluded; `possible` that exclusion was intended.
